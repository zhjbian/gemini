交付物：一体化恢复脚本

PyTools/jobs/mw_dom_recover_and_recompute.py —— 把原先分散的三件事串成一条龙，一条命令跑完全量。

背景约束（决定了方案可行性）

MotiveWave 导出的 DOM 文件一旦损坏，无法重新导出 —— dxFeed 数据源不提供历史深度（DOM/订单簿）回放。已验证：MW 本地存储 ~/Library/MotiveWave/historical_data/DXFEED/ 只保留 tick_data（17,874 个文件）与 bar_data*，没有任何 depth/DOM 数据。Tick 可以回补，DOM 只能实时抓取 —— 所以损坏的 DOM 是"抢救"而不是"重下"。

可行的原因是：MW 的 DOM 文件是多成员 gzip（concatenated gzip members）。导出被中断时，只有最后一个成员被截断，之前的成员结构完整、可以逐个抢救出来。

三个步骤

步骤 动作 实现要点
1. 抢救 (salvage) 复用 mw_dom_salvage 的逐成员解析，从损坏文件中提取所有可用时段 逐成员扫描 1f 8b magic；对伪成员头（gz 数据里偶然出现的 1f 8b）做过滤：解出的数据量 < 1 MB 即判定为噪声并忽略
2. 替换 (replace) 原文件改名为 *.broken 备份，抢救结果改名为正式的 _DOM.csv.gz；同时删除该日的 .hourly_idx.json 让其重建 备份不删除，可回溯
3. 重算 (recompute) 对 dom_metrics 为 NULL 的 5m 信号重新调用 extract_5m_dom_metrics(date, 'HH:MM', window_mins=5, tick_bins=None, tick_trades=None)，把结果写回 order_flow_signals.dom_metrics 见下方两处必须的修正

重算实现中必须处理的两个坑

坑 1：numpy 标量不可 JSON 序列化。 extract_5m_dom_metrics() 返回的是 numpy 标量（np.float64、np.False_），直接 json.dumps() 会抛 Object of type bool is not JSON serializable。修法是加递归转换：

def _json_safe(o):
    # dict -> 逐值递归; list/tuple -> 逐项递归; numpy 标量 -> .item()
    ...

并在写库前对整个 dom_metrics 走一遍 _json_safe()。

坑 2：必须拒绝空样本而不是写 0。 如果某时刻在抢救出的数据里没有覆盖（例如只剩晚间时段，RTH 已丢失），extract_5m_dom_metrics() 会返回一份"样本数为 0"的指标对象。若把它写进库，等于用全 0 覆盖掉"缺失"这一事实，指标会假性可用。因此加了硬性守卫：

if dm is None or int(dm.get("samples_count") or 0) == 0:
    continue   # 保持 NULL, 不写 0

日期格式：extract_5m_dom_metrics 要求 date 为 YYYY-MM-DD，而 MW 文件名用的是 YYYYMMDD，转换在调用前完成。

命令行

# 处理全部损坏文件（推荐）
python3 PyTools/jobs/mw_dom_recover_and_recompute.py --all

# 只处理指定日期（可重复传 --date）
python3 PyTools/jobs/mw_dom_recover_and_recompute.py --date 20260908

# 演练：不改文件、不改数据库
python3 PyTools/jobs/mw_dom_recover_and_recompute.py --all --dry-run

# 只抢救+替换，不重算（重算慢，可拆开跑）
python3 PyTools/jobs/mw_dom_recover_and_recompute.py --all --skip-recompute

参数：--all / --date YYYYMMDD（可多次）/ --ticker（配合 --date，默认 ES）/ --raw-dir / --dry-run / --skip-recompute。

保真度说明（哪些指标是完整恢复、哪些是近似）

extract_5m_dom_metrics() 只依赖 DOM 文件（订单簿快照），因此：

  • 完整恢复 ✅：book_flip_bull / book_flip_bear（盘口买卖大翻转）、iceberg_*（密集冰山）、vacuum_*（真空）、weighted_imbalance（加权失衡）等核心盘口指标。
  • 近似 ⚠️：spoof / absorption 等 tick 衍生项。原 sentinel 调用时会额外传入由 TICKS 解析出的 tick_bins / tick_trades 做增强；本次重算走 DOM 文件内的默认路径（tick_bins=None, tick_trades=None）。若要 100% 一致需重新解析 TICKS —— 已留作后续增强项。

⚠️ 关键发现（本次核查新发现）：替换步骤会让 MW 正在写的文件「孤儿化」

现象

今日（2026-09-10）核查文件状态时发现：

文件 大小 20 秒后 结论
ES_20260910_DOM.csv.gz 3,872,405 3,872,405 冻结（mtime 停在 00:26）
ES_20260910_DOM.csv.gz.broken 36,810,612 36,872,382 持续增长（+61,770 字节 / 20 秒）

lsof 给出决定性证据 —— MotiveWave (pid 32405) 仍持有 .broken 文件的打开句柄：

MotiveWav 32405 REG .../Raw/NQ_20260910_DOM.csv.gz.broken
MotiveWav 32405 REG .../Raw/ES_20260910_DOM.csv.gz.broken

根因

步骤 2 的"替换"是 rename 原文件 + 在新路径写抢救结果。当 MW 仍以打开的文件描述符持有原 inode 时：

  1. rename(原文件 → *.broken) —— MW 的 fd 跟着 inode 走，不受路径变化影响；
  2. 在正式路径上新建抢救结果文件；
  3. 此后 MW 的实时写入全部落进 *.broken，而系统按正式路径读取，只能看到步骤 2 那一刻的静态快照。

本次运行发生在 2026-09-10 00:0x PT —— 恰逢 MW 刚为新的交易日（09-10，UTC 07:00 = PT 00:00 起算）建好文件、正在写入。于是那一整天的 DOM 流都被写进了 .broken。

这条机制同时解释了历史上反复出现的"gzip 头合法、中途 invalid block type"型损坏：在 MW 运行期间对打开中的文件做 rename+replace，会让数据流与实际路径脱节，之后按正式路径读取时看到的正是"头正常、中途断裂"的文件。

影响与现状

  • 不是数据丢失：09-10 的全部 DOM 内容都在 ES_20260910_DOM.csv.gz.broken（36.8 MB 且在增长）与 NQ_20260910_DOM.csv.gz.broken（6.0 MB）里。
  • 是数据错位：系统按正式路径读到的是仅覆盖 07:00:00 → 07:06:14 UTC（即 00:00–00:06 PT）的 260,679 行快照，今天 RTH 的盘口数据对系统不可见（09-10 的 7 条信号全部 weighted_imbalance 缺失 → 0%）。
  • 修复方式是把 .broken 改回正式路径（MW 的 fd 跟随 inode，改回后写入即重新可见），并把当前那份冻结快照另存。因涉及对 MW 打开中的文件做操作，须人工确认后执行。

应当补上的防护（建议）

  1. 替换前检测目标文件是否正在被写入（比较两次采样的大小 / lsof / mtime 新鲜度），活跃则只做抢救不替换（抢救结果留在 Recovered/）；
  2. 或改为 copy 而非 rename（但这样 MW 仍写旧 inode，需配合让 MW 重新打开文件）；
  3. 最稳妥：把"替换"限定在MW 已退出或该日文件已停止增长时执行，作为离线维护步骤。
