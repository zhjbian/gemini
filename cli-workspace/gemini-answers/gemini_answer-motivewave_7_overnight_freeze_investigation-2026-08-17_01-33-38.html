motivewave_7_overnight_freeze_investigation

Question

MW 7.0.29 overnight session, ES/NQ chart freeze, price doesn't change, why?
here is log file /Users/zhijiebian/Library/MotiveWave/output/output (Aug-17 003832).txt

Answer

通过对日志文件 /Users/zhijiebian/Library/MotiveWave/output/output (Aug-17 003832).txt 的系统分析，导致当前 ES / NQ 隔夜时段图表卡死（Freeze）、价格不更新的核心原因如下：

一、 核心原因分析

1. 自定义指标 StudyBigTrades 频繁调用同步获取 Tick 导致线程严重阻塞

在日志中出现了大量如下耗时警告和调用栈：

01:02:16.778 WARNING HistData::getTickData() NQU26 ticks: 5119 elapsed: 16032 ms
01:02:37.246 WARNING HistData::getTickData() NQU26 ticks: 5119 elapsed: 20442 ms
...
at com.motivewave.platform.sdk.common.Instrument.getTicks(Instrument.java:240)
at bbt.StudyBigTrades.calculate(StudyBigTrades.java:212)
  • 瓶颈点：StudyBigTrades.java 第 212 行 instrument.getTicks(startTime, endTime) 在每个 Bar 或收到 Tick 时都会被触发。
  • 现象：在隔夜时段（特别是 00:00 - 01:00 跨日结算期间），MotiveWave 底层从本地磁盘/内存检索数千条 Tick 数据单次耗时达到 16~20 秒。在 01:03 附近，系统在几十秒内密集发起了上百次耗时 800ms~2000ms 的 getTickData 调用，直接占满了 MotiveWave 的后台线程池与 UI 事件分发队列，导致实时行情 Tick 积压无法推送到图表渲染层。

2. 跨日 Tick 数据写入异常（Incomplete Tick File）

日志在 01:05:01 报出了异常：

writeTicks() possibly incomplete file /ESU26 start: 08/17/2026 12:00:00 AM - 08/17/2026 12:48:42 AM
writeTicks() possibly incomplete file /NQU26 start: 08/17/2026 12:00:00 AM - 08/17/2026 12:48:42 AM
  • 当天凌晨跨过 00:00 后，MotiveWave 正在对前一日至当日凌晨的 Tick 文件进行切片与持久化，此时大量并发的 getTicks 请求与写入产生冲突，触发异常并锁定了实时行情写入通道。

3. 后台正在进行超大规模历史 Tick 数据回填（Backfill Storm）

日志显示，系统在后台从 AWS S3 连续下载并解压从 2 月份到 8 月份数个月的历史 Tick 压缩包（Backfill::downloadTickFile() ...），并在 01:01 出现 NoHttpResponseException 网络重试。该后台任务占用了极高的磁盘 I/O 和 CPU，进一步加剧了图表卡顿。

4. 本地历史数据缓存文件过多

启动时日志提示：

WARNING HistData::getDataFiles() ... excessive number of files returned: 8577 consider clearing the local data

本地积累了超过 8000+ 个历史数据切片文件，导致每次底层查找 Tick 时文件系统检索极为缓慢。

二、 临时恢复方案（立即解决当前卡死）

  1. 重启 MotiveWave 并断开/重新连接 dxFeed 数据源。
  2. 清除本地缓存历史数据：
    * 在 MotiveWave 菜单栏中依次点击：Configure -> Preferences -> General -> Historical Data -> 点击 Clear Cache / Clear Local Data。
  3. 临时在卡住的 ES/NQ 图表上移除或隐藏 BBT Big Trades Study，观察实时价格是否立即恢复跳动。

三、 代码与系统层面长效优化建议

  1. 优化 StudyBigTrades.java 的 Tick 获取逻辑：
    * 避免在 calculate() 或 onTick() 中反复全量调用 instrument.getTicks(startTime, endTime)。
    * 可以改用增量缓存，或仅在必要时（如历史初次加载时）批量拉取，而在实时运行期通过监听回调维护近期 Ticks。
  2. 限制回填范围：
    * 在 MotiveWave Workspace 设置中，将 Futures 的默认回填范围（Historical Data Range）调整为较短周期（如 5~10 天），避免每次启动触发数个月的 Tick 级全量回填。

mw7_vs_mw6_9_freeze_comparison

Question

但是在MW6.9的版本时 没有这样的问题

Answer

从 MotiveWave 6.9 到 7.0 的架构重构来看，导致在 6.9 正常而在 7.0.29 出现该问题的核心原因主要有以下几点：

1. 7.0 重构了底层 Tick 缓存机制（从“内存缓存”变为“分片文件强制校验”）

  • 6.9 的机制：
  • 6.9 对日内活跃品种（特别是正在绘制的图表）维护了常驻内存的 Ring-Buffer。当自定义指标调用 instrument.getTicks(startTime, endTime) 时，绝大部分当天/当前 Bar 的请求直接命中内存，耗时为 0~1 毫秒，不会触发磁盘 I/O。
  • 7.0 的变化：
  • 7.0 引入了全新的 Order Flow 与 Tick 存储引擎，将 Tick 数据按小时/日期切片压缩（如日志中的 1786939200000.tick_data.zip 和 .bar_data1）。
  • 7.0 在调用 getTicks() 时增加了完整性校验（Integrity Check）与间隙回填（Gap Filling）。在隔夜/跨日结算时段，如果当前文件未完成 flush（日志中报错 writeTicks() possibly incomplete file），7.0 会强制触发同步的磁盘解压与文件检索，导致单次调用耗时从 6.9 的 <1ms 暴增至 7.0 的 800ms ~ 20000ms（20秒）。

2. 7.0 数据分发线程锁机制变化（DataLoader / ThreadPool 同步锁）

  • 6.9：实时行情推送（LiveTicker）与指标计算（Study Execution）在部分数据流上是相对独立的管道，即使某个 Study 执行慢，实时 Tick 仍能更新到价格坐标轴和最新 K 线上。
  • 7.0：
  • 从 7.0 日志中的调用链可以看到：
    text DataLoader.onTick -> DataSource.a -> ConcurrentList -> Study.calculateValues -> Instrument.getTicks
  • 7.0 采用了更严格的 DataSource 管道同步机制。当 StudyBigTrades 在 Instrument.getTicks 上被阻塞时，它持有了该数据流的调度锁，导致后续到达的实时 Tick 无法被 LiveTicker 推送至 UI 渲染线程，表现为整个图表与最新价格完全“静止/冻结”。

3. 7.0 增强了历史缺失数据的自动主动回填（Aggressive S3 Backfill）

  • 7.0 会在后台自动探测本地缺失的 Tick 切片并向云端发起大量下载（日志中一次性触发了过去半年数十个 Tick Zip 包的下载）。
  • 当后台回填占用大量磁盘与网络资源时，正好与指标频繁读取当天 Tick 产生严重的文件系统锁竞争（I/O Contention）。

建议针对 7.0 的应对调整

  1. 关闭/限制自动深度回填：
    * 打开 Configure -> Preferences -> General -> Historical Data，检查是否勾选了针对 Order Flow / Ticks 的过长自动回填选项。
  2. 在 StudyBigTrades.java 中规避同步 getTicks：
    * 7.0 的官方最佳实践更推荐在 calculate(int index, DataContext ctx) 中通过 DataContext / Bar 的内置数据或增量事件获取，而非频繁同步调用 instrument.getTicks(start, end)。
    * 如果仅需当前 Bar 的 Tick 数据，可做时间戳过滤保护，避免在跨日（00:00 - 01:00）请求未完全持久化的时间区间。
