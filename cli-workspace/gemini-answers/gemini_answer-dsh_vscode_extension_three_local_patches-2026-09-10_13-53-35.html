总览

给 VS Code 扩展 skymecode.deepseek-harness-for-vscode 打的是本地补丁：直接改扩展包内的成品文件（dist/webview/chat.js、media/chat.css）。扩展每次升级都会覆盖这些文件，所以补丁用一个幂等脚本统一重打：python3 scripts/repatch_vscode_changes_bar.py。

按功能分 3 个项，共 4 条编号补丁：

项 补丁 目标文件 一句话
项一 变更卡片 补丁1（真 bug 修复）+ 补丁2（彻底隐藏） dist/webview/chat.js / media/chat.css "N files edited" 卡片折叠失效，干脆修好并隐藏
项二 最终结果分割线 补丁3 media/chat.css 在"分析步骤"与"最终结果"之间加醒目分割线，末尾补橙色收尾线
项三 历史列表点击 补丁4 dist/webview/chat.js 聊天历史列表"点不动、要多点几次"，重渲染竞态导致 click 丢失

统一的注入机制（三条约定）

  1. 标记块：每段注入内容都带 /* ===== BBT local patch: ... (start) ===== */ ... (end) */，脚本靠标记判幂等，重复执行输出"已打过 ✓"。
  2. 原始备份：首次打补丁时把原始文件复制成 *.bbt-bak（只创建一次，永不被后续补丁覆盖），所以 .bbt-bak 永远是最原始的版本，--revert 能一键还原。
  3. 语法校验：每次写盘后对 chat.js 跑 node --check，并回读文件确认各补丁标记都在。
文件 当前大小 原始备份 *.bbt-bak
dist/webview/chat.js 376,852 B 373,517 B
media/chat.css 116,736 B 112,966 B

生效方式（三个补丁通用）

Cmd+Shift+P → Developer: Reload Window。webview 资源有缓存，只关闭/重开面板往往不够。

项一 · 变更卡片（补丁1 + 补丁2）

问题是什么

聊天面板底部的 "N files edited"（changes-bar）卡片有两个问题：

  • 折叠失效（真 bug）：压缩后的 kl() 里，文件列表容器 changes-detail 无论展开与否都会被 t.append(...) 追加；变量 r（展开态）只控制"显示前 3 个"还是"全部"。而 "Show N files" 按钮仅在 !r && files.length > 3 时才出现 —— 于是文件数 ≤ 3 时（例如 "1 files edited"）点击摘要行没有任何可见变化，看起来像坏了。
  • 卡片本身不需要：日常使用中它占位且无信息量。

怎么修复

  • 补丁1（JS，变量名自适应、抗压缩改名）：在 changes-detail 容器被 append 之前，按同一个展开态变量切换 hidden 类（扩展自带 .hidden{display:none!important}）：

js // 注入形式（脚本按锚点定位并插入，变量名从原文抽取） <listVar>.classList.toggle("hidden",!<expandVar>),

锚点：let <VAR> = Me(e.document,"div","changes-detail") 找容器变量、aria-expanded",String(<VAR>) 找展开态变量，再定位其后第一处 t.append(<LIST_VAR>) 插入。幂等判据：正则 \w+\.classList\.toggle\("hidden",!\w+\),t\.append\(。

  • 补丁2（CSS）：向 media/chat.css 追加

css /* ===== BBT local patch (start) ===== * 隐藏 "N files edited" 变更卡片。 * 想保留卡片可见但修复折叠 bug: 用 --no-hide 重跑，或直接删除本段。 */ .changes-bar { display: none !important; } /* ===== BBT local patch (end) ===== */

全部还原成未打补丁的原始文件 python3 scripts/repatch_vscode_changes_bar.py --revert

项二 · "最终结果"分割线（补丁3）

问题是什么

聊天记录里，"上面的分析步骤"（Thought for Xs 折叠块、Bash 工具卡片）与"最终结果"之间几乎没有视觉分界，长回答里很难一眼定位结论。

排查发现：扩展本来就有这条分割线，只是弱到看不见 —— media/chat.css 里两条规则都只有 1px solid + widget-border 65%：

.message:has(.message-copy-footer):not(:has(.reasoning-block)) { ... border-top: 1px solid color-mix(... 65% ...); }
.message:has(.message-copy-footer) .message-body > .reasoning-block + .content-block { ... border-top: 1px solid ...; }

所以这项不是"新增"，而是把它做成醒目。

DOM 依据（读 dist/webview/chat.js 后确认）

.messages 下是扁平条目列表：.message（内部 div.message-body，子元素依次是 details.reasoning-block / div.content-block.text.markdown-body）与 div.tool-item、div.notice 是兄弟；button.message-copy-footer 只挂在"最后一条有结论的 assistant 消息"上。因此分两种情形：

  • 情形A（最常见）：结论消息自带 thinking → 线画在 reasoning-block + content-block 之间
  • 情形B：结论消息没有 thinking → 线落在答案文字上方，隔开上面的工具卡片

怎么修复

覆盖为实心 magenta 3px（无渐变） + 居中发光"最终结果"标签；并在答案结束处补一条同风格实心橙线，把本轮与后续内容分开（"最终结果"被紫线/橙线夹成闭环）。

关键 CSS（media/chat.css 末尾，标记块内）：

设计取舍（迭代过程）：先做成主题蓝 #4c8cff 渐变淡出 → 实测"不够醒目" → 改为实心 magenta、无渐变；随后按要求补橙色收尾线。每一轮回答都带线（不只整段对话最后一次）：判据是"该 assistant 消息后面不再跟 .tool-item / .notice"（即本轮收尾的回答），而不是扩展自带的 copy-footer 判据（后者只存在于最后一次回答）。

橙色收尾线是最终确认的版本。若只想保留线条、不要标签：删掉 ::before 的 content 行；想换色：改两处 #ff00ff / #ffa500。

项三 · 聊天历史列表"点不动"（补丁4）

问题是什么

Chat history 列表里的会话项大部分时候点不动：点击后没有反应，要反复点好几次、偶然才切换成功。有会话正在运行时（列表项右上角有蓝点）尤其明显。

根因（代码证据）

行本身是有监听器的按钮：

// 真正干活的监听器
button.session-row  →  addEventListener("click", () => U("selectSession", { sessionId: s.id }))

// 但列表在任何状态更新时都**整体重建**：
g.historyPanel.classList.contains("hidden") || pt()      // pt() 重建全部 session-row 节点

只要按下与抬起之间节点被替换，浏览器就不再派发 click（click 要求 mousedown/mouseup 命中同一节点或共同祖先；重建后共同祖先变成没有监听器的容器）→ selectSession 永不触发。会话在跑时状态更新最密集，所以最难切换。这不是热区/层级问题（.session-row-actions 悬停时 pointer-events:auto 只覆盖右上角一小块）。

怎么修复（三层，全部带超时自愈）

层 机制
① 治本 pt() 加守卫 if(!z||(window.__bbtRowPressUntil||0)>Date.now())return —— 按下期间冻结列表重建，让原生 click 正常落地
② 兜底 delegated pointerup：若行节点已被替换或未命中按钮，对保留的元素引用补一次 .click()（元素即使已脱离 DOM，其监听器仍会执行 → selectSession 照常工作）
③ 死区 .session-row-wrap 内、按钮之外的区域（含 session-row-actions 的空隙）点击代打按钮

注入内容（dist/webview/chat.js，两处改动）：

// 改动一：pt() 重建守卫（唯一锚点，命中 1 次）
function pt(){if(!z||(window.__bbtRowPressUntil||0)>Date.now())return;let e=g.historySearch.value.trim()

// 改动二：文件末尾追加 delegated 兜底（完整块）
(function () {
  if (window.__bbtHistRowFix) { return; }
  window.__bbtHistRowFix = true;
  var WRAP = ".session-row-wrap", ROW = ".session-row",
      ACT = ".session-row-actions, .session-worktree-action";
  var press = null;
  function closest(el, sel) { return (el && el.closest) ? el.closest(sel) : null; }
  function isAction(el) { return !!closest(el, ACT); }
  function freeze(ms) { window.__bbtRowPressUntil = Date.now() + ms; }
  document.addEventListener("pointerdown", function (ev) {
    press = null;
    if (ev.button !== 0) { return; }
    var t = ev.target, wrap = closest(t, WRAP);
    if (!wrap) { return; }
    freeze(1500);                       /* 按下即冻结列表重建（含操作按钮） */
    if (isAction(t)) { return; }        /* 操作按钮只冻结，不代打（否则会误切会话） */
    var row = closest(t, ROW) || wrap.querySelector(ROW);
    if (!row) { return; }
    press = { row: row, x: ev.clientX, y: ev.clientY, t: Date.now() };
  }, true);
  document.addEventListener("pointerup", function (ev) {
    var p = press; press = null;
    if ((window.__bbtRowPressUntil || 0) > Date.now()) { freeze(300); }  /* 覆盖紧随其后的 click */
    if (!p || Date.now() - p.t > 1200) { return; }
    if (Math.abs(ev.clientX - p.x) > 6 || Math.abs(ev.clientY - p.y) > 6) { return; } /* 拖动/滚动不算点击 */
    var t = ev.target;
    if (closest(t, ROW) === p.row && p.row.isConnected) { return; }     /* 原生 click 会送达 */
    try { p.row.click(); } catch (e) {}                                 /* 节点被换掉/命中死区 → 补一次 */
  }, true);
  document.addEventListener("pointercancel", function () { press = null; freeze(0); }, true);
  document.addEventListener("click", function (ev) {
    var t = ev.target, wrap = closest(t, WRAP);
    if (!wrap || isAction(t) || closest(t, ROW)) { return; }
    var row = wrap.querySelector(ROW);
    if (row) { ev.preventDefault(); ev.stopPropagation(); row.click(); }
  }, true);
})();

边界处理：操作按钮（pin / 标签 / 归档 / worktree）只冻结不代打，避免把"归档"点成"切换会话"；位移 > 6px 视为拖动/滚动不算点击；节点完好时不重复触发；冻结用时间戳而非布尔标志，即使 pointerup 丢失也会 1.5 秒后自愈，不会永久冻结列表。

残余风险（已知边界）

宿主侧还有一条静默失败路径：

selectSession(e){ if(this.summaries.has(e)||await this.refreshSessionList(), !this.summaries.has(e)) throw new Error("Session not found.") }

若会话不在 summaries 且刷新后仍没有，会抛异常而 UI 无提示。若重载后仍偶发"点了没反应"，问题在这条（而非点击丢失），建议给它加重试 + 可见提示。

生效方式与"扩展升级后怎么办"

  1. 打完补丁后 Cmd+Shift+P → Developer: Reload Window（webview 资源有缓存）。
  2. 扩展升级会整目录替换，补丁与 *.bbt-bak 一并消失 —— 重新执行 python3 scripts/repatch_vscode_changes_bar.py 即可（它会重新备份新版本的原始文件并重打四条补丁）。
  3. 若脚本报 ✗ 锚点未找到，说明扩展内部结构变了（大概率是压缩变量名或函数名改动），需人工核对后更新脚本里的锚点；脚本会明确指出是哪个补丁、哪个文件。
