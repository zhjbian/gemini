### 3.1 容错读取器对照（本轮最有价值的一击）

对同一份 DOM 文件分别用**标准库 `gzip.open`**（旧口径）与 **`gz_tolerant.scan_gz`**（新口径）读取：

```console
$ python3 /tmp/paw_gz_compare.py
### 20260911  size=182,095,436 B
  旧口径(gzip.open) 读到 0 行后中断 · 耗时 0.0s · 错误: error: Error -3 while decompressing data: invalid block type
  新口径(scan_gz)   rows=17,483,137 lines=17,483,138 members_ok=0 members_bad=5 bytes_skipped=114,086,537 耗时 5.6s
  first_ms=1789133188364 last_ms=1789160393292
### 20260916  size=546,399,463 B
  旧口径(gzip.open) 读到 0 行后中断 · 耗时 0.0s · 错误: error: Error -3 while decompressing data: invalid block type
  新口径(scan_gz)   rows=43,696,592 lines=43,696,593 members_ok=0 members_bad=12 bytes_skipped=382,339,396 耗时 13.4s
  first_ms=1789566523395 last_ms=1789622776281
```

**对照结论**：

| 数据日 | 文件大小 | 旧口径（`gzip.open`） | 新口径（`scan_gz`） |
| :--- | ---: | :--- | :--- |
| 2026-09-11 | 182,095,436 B | **0 行** + `invalid block type` | **17,483,137 行**（`members_bad=5`，跳过 114 MB，5.6 s） |
| 2026-09-16 | 546,399,463 B | **0 行** + 同一错误 | **43,696,592 行**（`members_bad=12`，跳过 382 MB，13.4 s） |

> **口径说明**：两天 `members_ok = 0` —— 即**没有任何一个成员正常收尾**（多写者交错写坏）。09-16 在重算作业中的探测为 `members_bad=6 / 跳过 379 MB`，本次复核为 `12 / 382 MB`，差异来自**该文件当时仍在被 MW 写入**（复核时 mtime 22:25，文件仍在增长）；两者量级一致。

⇒ 这正是「旧口径把**上千万行可读数据**判成 0」的机制：**一个成员坏 = 整份读取终止**。

## 7. 结论

1. **问题定性准确**：PAW 累积统计卡片**概念上不可替代**（把"墙 / 吸收"从描述性维度升级为判据的唯一标定来源，并产出选行权价的"安全距离"），但**改造前形态基本没有意义** —— 没在累积、n=1 也显示 100%、无任何决策层消费。
2. **真正的根因不在页面而在管道**：标准库 `gzip.open` 只要在**任一 gzip 成员**上抛 `zlib.error` 就**整份终止**；09-11 / 09-16 因此被判"读取失败"、当日 0 事件，而文件里其实有 **1,748 万 / 4,370 万行**可读。超时侧 `1800 s` 不够（09-14 / 09-15 双双 `TimeoutExpired`）。
3. **修复已落地并验证 14/14**：容错读取器（`gz_tolerant.py`）让"成员损坏"从**致命**降级为**警告**；单日 **0 → 50**；全量重算后 **266 事件 / 264 E1 / 305 基准**，09-11 **0→35**、09-14 **失败→33**、09-15 **失败→52**、09-16 **0→50**。
4. **语义修正到位**：`n<30` 不再给百分比（页面显示"样本不足（n=1）"），所有百分比都带**随机基准 / p 值 / 来源日**；门槛口径拆分「可用日」（9/10）与「**有事件日**」（6/10），消除"已积累很多天"的错觉。E1 30 分钟 **12.5% vs 基准 3.36%（n=298），p<0.0001** 是目前唯一可用且显著的基础率结论；ASK 侧强于 BID 侧（BID 60/120 分 `p=0.75/0.92` 与基准无异）。
5. **页面归属归位**：`/bbt_signals`（数据健康）已无 `paw-stats-card`；新 section 紧随 `#ofDeepCard`（pattern 匹配）之后，支持折叠、`?paw=1` 深链、右上刷新，**收起态徽标**即显示 `E2/E3 2/30 · 有事件日 6/10`，并明确标注"仅研究标定，不参与自动下单"。
6. **未做且刻意不做**：**P3（把安全距离接进卖家系统）** —— 全仓确认无消费方、"Setup 5" 不存在，接入需用户先定设计（方向 / 时限 / 闸门），本轮只报告。
7. **一条可复用的方法论**：**"有产物"不等于"在累积"**。判断累积是否真实，必须同时看 ① 逐日 `status` 与 `note`、② **真正产出事件的天数**（而不是 status==ok 的天数）、③ 每个百分比的**样本来源日与随机基准**。本轮 09-11 / 09-16 的"ok / 0 事件"与 `usable_days_n=6` 的"像已积累很多天"，正是这三条同时缺失时的典型误判。
